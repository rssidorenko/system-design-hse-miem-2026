# Проектирование электронной системы для учеников, родителей и преподавателей начальной школы
## Модули и интеграции
В качестве подхода к разработке модели ПО применяем **Domain Driven Design**, так как при проектировании такой системы крайне важно следование бизнес-логике (система должна быть интуитивно понятной и удобной в использовании). Для реализации сложной SaaS-системы, которая позволит объединять изолированные друг от друга школы, следует также рассмотреть микросервисный подход к проектированию архитектуры.

### Домены и сущности
1. Контекст **"Управление пользователями и школами"**  
   Ответственность: регистрация, авторизация, управление профилями, ролями, школами.  
   Сущности: школа, пользователь, роль пользователя, учащийся (должен быть связан со школой и родителями), класс. Пользователи могут быть связаны сразу с несколькими учащимися в разных классах.

2. Контекст **"Управление образовательным процессом"**
   Ответственность: ведение журнала посещаемости, внесение оценок и заданий
   Сущности: Преподаватель, учащийся, предмет, присутствие, оценка, номер задания, формулировка задания

3. Контекст **"Управление форумом"**
   Ответственность: функционирование форума для родителей и преподавателей
   Сущности: класс, пользователь, сообщение, вложение

4. Контекст **"Хранение файлов"**
   Ответственность: хранение файлов, добавленных пользователями
   Сущности: пользователь, вложение

5. Контекст **"Визуализация данных"**
   Ответственность: подготовка отчётов, запрошеннных пользователями
   Сущности: пользователь, отчёт

### Описание модулей
1. **Сервис API Gateway**  
   Сервис будет использоваться в качестве единой точки входа в приложение для пользователей. Он проверяет токены, маршрутизирует запросы к нужным внутренним сервисам, а также выполняет функции ограничения входящей нагрузки и логирования данных.
3. **Сервис авторизации и аутентификации**  
  Необходим для регистрации и входа пользователей в приложение. Следует отметить, что сервис должен быть stateless с хранением JWT-токенов, чтобы пользователям не приходилось каждый раз при входе в приложение заново регистрироваться.
4. **Сервис управления профилями пользователей**  
   Требуется для создания, изменения и удаления профилей пользователей, актуализации данных в них, назначения и изменения ролей, предоставления прав доступа.
5. **Сервис для отслеживания действий пользователей**
   Процесс контроля необходим для осуществления логирования и обнаружения ошибок.
6. **Сервис для внесения данных пользователями**  
   Будет применяться для добавления информации преподавателями (посещаемость, оценки, задания) и родителями (информация об отсутствии учеников). Через этот же сервис будут загружаться и файлы (изображения, документы и т. д.)
7. **Сервис для обмена сообщениями**  
   Необходим для функционирования чата для преподавателей и родителей.
8. **Сервис для хранения документов и изображений**  
   Будет использоваться для сохранения не текстовых данных в приложении.
9. **Сервис для формирования и выгрузки отчётов**  
   Требуется для поддержания работоспособности функционала по выгрузке Excel-отчётов из приложения.

### Интеграции
1. **Сервис API Gateway**: синхронный REST / gRPC-запрос для моментального входа в систему.
2. **Сервис авторизации и аутентификации**: синхронный REST / gRPC-запрос для авторизации сразу после создания запроса.
3. **Сервис управления профилями пользователей**: все операции, производимые профилем должны быть синхронными, чтобы пользователь сразу видел результат. Особенно существенно это в контексте операций понижения уровней доступа и удаления аккаунтов.
4. **Сервис для отслеживания действий пользователей**: асинхронный RabbitMQ / Kafka (или любой другой брокер сообщений), т.к. это очень ресурсозатратный процесс, который можно реализовывать с незначительной задержкой. Для повышения скорости можно применять, например, потоковую обработку Kafka Stream.
5. **Сервис для внесения данных пользователями**: синхронный REST / gRPC-запрос для моментального отображения результата выполненного действия (например, сразу должны отображаться посещаемость, выставленная оценка и факт загрузки файла в систему).
6. **Сервис для обмена сообщениями**: WebSocket, т.к. для корректного функционирования чата необходим постоянно работающий двунаправленный канал связи между клиентом и сервером.
7. **Сервис для хранения документов и изображений**: синхронный REST / gRPC-запрос, т.к. данные должны сохраняться моментально для дальнейшего отображения в системе.
8. **Сервис для формирования и выгрузки отчётов**: синхронный REST / gRPC-запрос данных из хранилища в момент создания заявки на генерацию отчёта. Сама же генерация отчёта может занять определённое время и быть асинхронной.

### Взаимодействие между модулями
В рассматриваемой нами системе могут быть следующие варианты взаимодействия между модулями.
|Взаимодействующие модули|Описание взаимодействия|Подходящий механизм|Обоснование|
|------------------|------------------|------------------|------------------|
|Сервис API Gateway --> Сервис авторизации и аутентификации|Проверка токена, аутентификация пользователя|Синхронный REST / gRPC|Необходим немедленный ответ для доступа к ресурсу.|
|Сервис API Gateway --> Сервис управления профилями пользователей|CRUD операции с профилями и ролями|Синхронный REST / gRPC|Администратор должен сразу видеть изменения.|
|Сервис API Gateway --> Сервис для внесения данных пользователями|Внесение/просмотр оценок, посещаемости, загрузка документов|Синхронный REST / gRPC|Пользователь ожидает мгновенного отклика после внесения данных.|
|Сервис API Gateway --> Сервис для обмена сообщениями|Установка соединения между пользователями для бесперерывного обмена сообщениями в форуме|WebSocket|При использовании WebSocket'а создаётся двунаправленный канал для обмена сообщениями.|
|Сервис API Gateway --> Сервис для хранения документов и изображений|При загрузке пользователем сообщения они сохраняются в хранилище.|Синхронный REST / gRPC|Файл должен быть немедленно доступен после загрузки.|
|Сервис API Gateway --> для формирования и выгрузки отчётов|Создаётся запрос на создание отчёта и его выгрузку.|Синхронный REST / gRPC (с возможной асинхронной генерацией)|Требуется быстрый ответ о принятии запроса, асинхронная оперативная подготовка файла.|
|Все сервисы --> Сервис для отслеживания действий пользователей|Все события, происходящие в системе, записываются и логируются для отслеживания ошибок.|Асинхронный (через события в RabbitMQ или Kafka)|Логирование создаёт высокую нагрузку на систему, в связи с чем её лучше выполнять в асинхронном формате без блокировки ресурсов для более востребованных пользователями сервисов.|
|Сервис для обмена сообщениями и файлами --> Сервис для хранения документов и изображений|При загрузке файлов в систему (в частности, в форум) они попадают в хранилище с целью сохранения данных для будущего|Синхронное взаимодействие через REST / gRPC-запрос|Взаимодействие между сервисами осуществляется сразу после внесения файла в систему -- в частности, может создаваться событие, подтверждающее успешную загрузку файла.|
|Сервис для формирования и выгрузки отчётов --> Сервис для внесения данных пользователями|При запросе пользователя на формирование отчёта необходимо загрузить из хранилища данные о посещаемости и успеваемости отдельного ученика.|Синхронное взаимодействие через REST / gRPC-запрос|Данные запрашиваются из хранилища сразу после создания запроса пользователем. Тем не менее, в целях снижения нагрузки на систему формирование отчёта может происходить в асинхронном формате с небольшой задержкой.|
