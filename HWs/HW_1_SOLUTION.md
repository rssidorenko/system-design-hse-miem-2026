# ДЗ №1: Нагрузочное тестирование
## Цель работы
Провести нагрузочное тестирование, проанализировать метрики и найти "узкие места" (ботлнеки) в системе.

## Выбор метрик
Для отслеживания я выбрал следующие метрики:  
Дэшборд **Node Exporter Full**
1. CPU Busy
   Показывает долю времени, когда процессор выполнял полезную работу (не простаивал). При нагрузочном тестировании это один из основных индикаторов того, достиг ли бэкенд предела своих вычислительных ресурсов. Если показатель CPU Busy приближается к 90‑100%, дальнейшее увеличение нагрузки приведёт к росту задержек и отказов.
2. Sys Load
   Обозначает усреднённое количество процессов, ожидающих доступа к процессору. Значение более 100% свидетельствует о том, что система не справляется с потоком задач, и запросы начинают становиться в очередь.
3. Sockstat TCP
   Количество открытых TCP‑соединений в разных состояниях. Позволяет увидеть, не исчерпывается ли лимит сокетов при резких пиках нагрузки, не накапливаются ли зависшие соединения.

Дэшборд **Postgres Overview**
1. Rows
   Показывает интенсивность работы с данными: сколько строк в секунду читается и изменяется. Отражает, насколько сильно нагружена база данных.
2. Number of Active Connections
   Текущее количество активных клиентских подключений к PostgreSQL. Помогает увидеть, не упирается ли БД в настроенный лимит числа соединений. Если при повышении нагрузки этот показатель достигает максимального значения, новые запросы к базе начнут получать отказ или вставать в очередь.

Дэшборд **k6 Prometheus**
1. Performance Overview
   VUS (Virtual Users) -- число одновременно работающих виртуальных пользователей по сценарию. Позволяет оценить нагрузку на систему.
   http_req_s -- количество HTTP-запросов в секунду, которое проходит через систему. Показывает фактическую пропускную способность.
   http_req_s_errors -- скорость ошибочных запросов. Рост сигнализирует о деградации сервиса.
2. Transfer Rate
   Средняя скорость отправки (data_sent) и получения (data_received) данных k6. Позволяет оценить, сколько сетевого трафика генерирует нагрузка, и не упирается ли сетевой канал. Если при росте нагрузки скорость упирается в плато, а задержки растут, возможно, узким местом становится сеть, а не приложение или БД.
3. HTTP Request Rate
   Детализация RPS с разделением на успешные запросы (http_req_s_success) и ошибки (http_req_s_errors).

## Анализ и выводы
По результатам нагрузочного тестирования можно сформулировать несколько выводов.
1. Система сохраняет устойчивость в простое и восстанавливается после снятия нагрузки.  
   Во всех трёх сценариях после завершения теста показатели CPU, Load Average, TCP-соединений и метрик БД возвращались к исходным значениям. Это говорит об отсутствии утечек ресурсов и корректной работе механизмов очистки.
2. Основное узкое место -- вычислительные ресурсы единственного экземпляра бэкенда.  
   При каждом сценарии наблюдался резкий рост загрузки CPU (CPU Busy) и длины очереди процессов (Sys Load). В пиках нагрузка превышала возможности одного ядра / сервера, что приводило к задержкам и ошибкам. Sockstat TCP демонстрировал накопление соединений в состоянии TIME_WAIT, что косвенно подтверждает перегрузку сервера, не успевающего обрабатывать поступающие запросы.
3. База данных испытывает повышенную, но не критическую нагрузку.  
   Количество активных соединений с PostgreSQL росло во всех тестах, однако не достигло критического максимума. Интенсивность операций со строками (Rows) возрастала, но БД справлялась без падений. Тем не менее, высокое количество подключений может создавать конкуренцию за ресурсы и замедлять выполнение запросов, особенно при длительной нагрузке.
4. При росте нагрузки резко увеличивается доля ошибочных запросов.  
   На панелях Performance Overview и HTTP Request Rate видно, что с ростом VUs и RPS растёт и количество ошибок (http_req_s_errors). Таким образом, при достижении предела пропускной способности бэкенд не успевает обрабатывать часть запросов, поэтому они завершаются таймаутами или отказами.
5. Характер нагрузки влияет на скорость деградации.  
   - "Шторм" (1000 пользователей за 10 с) привёл к практически мгновенному всплеску ошибок: система не справилась с резким пиком.  
   - "Волна" (плавный рост до 500 пользователей) позволила дольше оставаться в рабочем состоянии, но всё равно показала рост ошибок при приближении к пику.  
   - "Плато" (200 пользователей в течение 3 минут) продемонстрировало, что даже умеренная, но продолжительная нагрузка вызывает накопление ошибок, вероятно, из-за постепенного исчерпания ресурсов или неоптимального использования соединений с БД.

**Основной вывод:** система работоспособна, но плохо масштабируется вертикально. Один инстанс бэкенда не способен выдержать заявленные пиковые нагрузки. База данных требует оптимизации, но не является первичным "узким местом".

## Предлагаемые решения
1. **Горизонтальное масштабирование бэкенда**  
Запустить несколько реплик бэкенда и настроить балансировку (например, HAProxy). Это позволит распределить нагрузку между экземплярами, снизить загрузку CPU на каждом из них и повысить отказоустойчивость.
2. **Ограничение и управление соединениями с БД**  
Внедрить пулер соединений (например, PgBouncer). Это ограничит максимальное количество подключений к PostgreSQL, уменьшит накладные расходы на установку новых соединений и предотвратит конкуренцию.
3. **Кэширование частых GET-запросов**  
Добавить Redis для кэширования списка заказов (GET /api/orders). Это снизит нагрузку на базу данных и ускорит ответы, особенно при повторяющихся чтениях.
4. **Оптимизация запросов и кода** 
Проанализировать медленные SQL-запросы, добавить недостающие индексы. Проверить, нет ли в коде приложения лишних ожиданий или неэффективных операций.
5. **Rate limiting на уровне API Gateway**
Настроить ограничение количества запросов от одного пользователя или IP на Nginx/HAProxy при их внедрении. Это поможет сгладить пики и не допустить лавинообразного отказа.
